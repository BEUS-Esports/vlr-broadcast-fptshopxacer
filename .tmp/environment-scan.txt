# FPT Shop x Acer - VLR Graphics Controller

Valorant broadcast graphics controller: SvelteKit 3, Svelte 5, Skeleton UI.

Manages teams, players, tournaments → matches → games and game resources, and drives seven graphics: Player Lineup, Player Stats, Map Veto, Agent Select, In-Game, Post-Game and MVP.

## Setup

Node 26.13.0 and pnpm 12.16.1 (`mise.toml`). Copy `.env.example` to `.env`, then:

```sh
pnpm install --frozen-lockfile
pnpm db:migrate
pnpm db:seed   # optional: 3 fictional teams, 18 players
pnpm dev
```

## Rules

- Change the schema only with reviewed migrations; the app applies them on startup after an automatic backup. Never `db:push` event data.
- Run `pnpm check`, `pnpm build` and E2E one after another; they share generated files. Use `PLAYWRIGHT_CHANNEL=chrome` for installed Chrome.
- Run one Node process. SSE and the live-provider session are process-local.
- Management routes have no sign-in (trusted LAN only). `/gfx/live/*` output pages have no controls.
- Keep provider keys and group codes out of public env vars, fixtures, OBS URLs, SSE, form responses and client data.
- Log server operations with `logEvent` and safe metadata only. Pass known credentials as the last argument so they are redacted:
  `logEvent('warn', 'example.failed', { provider }, cause, [accessKey, groupCode])`
- `ORIGIN` is read at startup: set it before `node build`, and restart when it changes. No rebuild.
- Back up the database, `ASSET_DIR` and the encryption key together.
- Team A/B is competition order. Swap Left/Right changes only presentation.
- Preview follows saved data. A shown graphic keeps its capture until **Update** (standalone) or **Update Live** (composite).

# Broadcast operation and production

## Controller

- The sidebar has **Preparation** (Teams, Players, Game Resources, Tournaments) and **GFX Control** (Global Settings plus the seven graphics).
- `/admin/graphics` is Global Settings. Each `/admin/graphics/<graphic>` page shares Global Setup and edits the same preparation data as normal management.
- Choose Tournament → Match → Game, then **Take game live**. Partial selector drafts and browsing in management don't change the live game.
- Hide every shown graphic before changing or clearing the live game. The server enforces this across controllers.

## Preview and Show

- Each page has an embedded 16:9 Preview and a **Large Preview** dialog. Both use the real output renderer.
- Preview always follows the latest saved data, including while the graphic is hidden.
- **Show** publishes a persisted capture of the graphic's saved preparation and content controls. Later saves update only Preview, and program keeps its capture. Pressing Show again keeps the capture; **Update** recaptures the latest saved version in place, without animating out and back in. **Hide** plays the graphic's out animation before it leaves.
- Explicit presentation and current-side changes apply live.
- An editor with unsaved changes keeps its original record and revision across a refresh or a remote selection change.
- Player Stats offers Single and Head-to-Head, scoped to a game, match or tournament. MVP uses the operator's saved pick.
- Missing preparation is shown as unavailable.

## Presentation

- Team A/B is competition order. **Swap Left/Right** changes only screen presentation.
- Current attackers/defenders set the blue/red colors without moving teams.
- Unknown tournament slugs use the generic test templates. A slug `<template>-<anything>` uses that template, so `predator-roadshow-val-dong-nai` uses `predator-roadshow-val`.
- A tournament template's `Graphic.svelte` may export `play()`, `stop()` and `update(snapshot)` to animate in, out and on data change. A template without `play`/`stop` gets a 150ms fade (0ms with reduced motion); `update` is optional, and without it new data just appears. Predator Roadshow animates in and out (400ms) and has no `update`.
- The Phase 5/5.1 native In-Game fallback passed real Valorant/OBS composition testing. The Phase 5/5.1 native/test package is the accepted fallback baseline; external-provider HUD acceptance is recorded separately.

## OBS URLs

Read-only, on a transparent 1920×1080 canvas:

| Graphic       | Route                     |
| ------------- | ------------------------- |
| Player Lineup | `/gfx/live/player-lineup` |
| Player Stats  | `/gfx/live/player-stats`  |
| Map Veto      | `/gfx/live/map-veto`      |
| Agent Select  | `/gfx/live/agent-select`  |
| In-Game       | `/gfx/live/in-game`       |

For rehearsal, `/gfx/live/composite` combines all seven in one output with shared connections. It has its own on-air state, independent of Show/Hide on the individual URLs.

- **Take Live** puts a graphic on the composite and captures its saved data. **Update Live** recaptures the latest saved data for a graphic already on air, and **Take Off** removes it with its out animation. The **Live Now — Composite** panel on Global Setup lists each layer and its occupant, with per-row Update and Take Off and **Clear composite**.
- Layers from back to front: 0 In-Game; 1 Player Lineup, Player Stats, Map Veto, Post-Game, MVP; 2 Agent Select. Each layer holds one graphic. Taking another graphic live on an occupied layer plays the old one's out animation first, then the new one's in animation. Graphics on different layers stack.
- Compare vMix performance before going on air with it. Keep the individual URLs as a rehearsed fallback.

## Production deployment

Use Node 26.13.0, pnpm 12.16.1 and `pnpm install --frozen-lockfile`. A clean Windows install and production build passed on 2026-11-03; the current lockfile needs no adapter patch.

Set `ORIGIN` to the exact address that controllers and OBS use when starting the server. adapter-node reads it at startup, so changing the address needs a restart, not a rebuild. In PowerShell:

```powershell
pnpm build
$env:ORIGIN = 'http://192.168.1.10:3000' # replace with the server LAN address
$env:HOST = '0.0.0.0'
$env:PORT = '3000'
node --env-file=.env build
```

At runtime:

- Keep `DATABASE_URL` and `ASSET_DIR` on persistent storage, and set `BODY_SIZE_LIMIT=160M` for uploads. Compose reads the operator's `.env`, so raise `BODY_SIZE_LIMIT` to `160M` there too.
- Before upgrading to the version with bundle import, run `pnpm db:duplicates`. It lists team and player names, tags and Riot IDs that differ only by case or by spaces around `#`. The startup migration adds unique indexes and refuses to apply over such duplicates, so fix them first. The script reads `DATABASE_URL` from the host's `.env` (`file:local.db`), not the compose database, so for the compose deployment run `DATABASE_URL=file:data/broadcast.db pnpm db:duplicates` from the repo on the host, with the app stopped (or against a backup copy).
- Run **one Node process**. SSE delivery is process-local, so several workers or replicas would need shared pub/sub.
- Prepared graphic captures are stored in the database and survive restarts.
- After deploying a new build, refresh every OBS browser source and open admin page. Output pages validate the live snapshot strictly, so one left open across a deploy that changed the snapshot shape stops updating.
- Authentication is deferred for trusted-LAN operation. Output pages have no controls, but anyone who can reach the management routes can write.

## Linux HTTPS deployment (Docker + Caddy)

VDO.Ninja camera iframes load only in a secure context, so OBS and vMix on other PCs need HTTPS. `compose.yaml` runs the app behind Caddy at `https://valorant-gfx.noibo.beusesports.vn`. Caddy gets a Let's Encrypt certificate through the Cloudflare DNS-01 challenge, so the server never needs to be reachable from the internet. It has its own certificate and token, independent of the shared internal web server.

Always open the app by hostname. `https://<IP>` gives a certificate error, and the app's own port is not published.

### One-time setup

1. Run `sudo systemctl enable --now docker.service`. With only `docker.socket` enabled, Docker starts on the first `docker` command, not at boot, so after a reboot the outputs would stay blank until someone ran one.
2. Reserve the server's LAN IP in DHCP. The reservation is per network interface: Wi-Fi and Ethernet have different MAC addresses, so reserve the one used on show day.
3. In Cloudflare, add an A record `valorant-gfx.noibo` → that IP, **DNS-only** (grey cloud). Cloudflare's proxy cannot reach a private IP. Add the same name → IP to every local DNS override that answers for it (AdGuard, MikroTik).
4. Create an API token with **Zone → DNS → Edit** for `beusesports.vn` only. Cloudflare scopes tokens per zone, so this token can edit any record in it. Keep it only on this machine.
5. `cp deploy/caddy/caddy.env.example deploy/caddy/caddy.env`, `chmod 600 deploy/caddy/caddy.env`, and paste the token. The file is gitignored, and the app container never sees it.
6. Keep `.env` as for any production run. Compose overrides `ORIGIN` and pins `DATABASE_URL=file:data/broadcast.db`, `ASSET_DIR=./data/assets` and `SETTINGS_ENCRYPTION_KEY_FILE=./data/settings.key`, so every data path stays inside the `./data` bind mount.
7. Prepare `./data` as your own user before the first start. The container runs as uid 1000, so `id -u` must print `1000`. If Docker has to create the directory itself, it is owned by root and the app cannot write to it.
   - Run `mkdir -p data/assets`.
   - To keep existing data, copy the database with `sqlite3 local.db ".backup data/broadcast.db"`. This is safe even while a dev server has `local.db` open.
   - For a new event database, leave `data/broadcast.db` absent. The app creates it and applies every migration on first start.

### Start, stop and logs

```bash
docker compose up -d --build
docker compose logs caddy | grep -i 'certificate obtained'   # first start only
docker compose logs -f app
docker compose down
```

Both services restart with Docker unless they were stopped. Before the show, check that `docker compose ps` lists `app` and `caddy` as running. The certificate and ACME account live in the `caddy_data` volume. Renewal needs internet roughly every 60 days, so start the stack once before travelling to an offline venue.

### Backups and upgrades

The database, assets and key stay in `./data`, so the host-side scripts work. Host commands read `.env`, and `.env` may still point at `local.db` for development. Always pass the event paths explicitly; the prefix wins over `.env`. Stop the app first:

```bash
export DATABASE_URL=file:data/broadcast.db ASSET_DIR=data/assets SETTINGS_ENCRYPTION_KEY_FILE=data/settings.key
docker compose stop app
pnpm backup -- --output <new-directory> --app-stopped
docker compose start app
```

To upgrade, between shows and never during one:

```bash
git rev-parse --short HEAD   # note the running version, for rolling back
git pull
docker compose up -d --build
docker compose logs app | grep -i migrations   # empty when nothing was pending
```

On start the app applies pending migrations by itself. If the database already has data, it first backs up the database and assets to `data/backups/<time>-before-<migration>/` (the log shows it as `/app/data/backups/…`). These backups are never pruned; delete old ones yourself. The encryption key is not copied into them; it stays in `data/settings.key`.

If the backup or a migration fails, nothing is applied and the app exits. It writes what failed, the backup path and the error to `data/backups/MIGRATION-FAILED`. Docker keeps restarting the app, but while that file exists, a start with pending migrations neither backs up nor migrates: it logs the failure and exits again, so one failure makes at most one backup. The data is untouched, so roll back only the code: `git checkout <noted version>`, then `docker compose up -d --build`. The old version has nothing pending and starts normally. Delete `data/backups/MIGRATION-FAILED` only when you want the next start to try the upgrade again with a fresh backup.

If the migration succeeded but the result is wrong, roll back the code **and** the data. Restoring only the data does not help: the new build would migrate it again on start. Check that the backup's `manifest.json` has `"complete": true`, then:

```bash
docker compose stop app
git checkout <noted version>
B=data/backups/<time>-before-<migration>
mv data/broadcast.db data/broadcast.db.rejected && mv data/assets data/assets.rejected
cp "$B/database.db" data/broadcast.db && cp -r "$B/assets" data/assets
docker compose up -d --build
```

Edits made after the upgrade are only in the `.rejected` copies. The [RHS runbook](./RHS-RUNBOOK.md) covers checking the restored outputs before going back on air.

Optional rehearsal: to preview what a migration changes on air (such as 0007 hiding shown graphics), copy the database with `sqlite3 data/broadcast.db ".backup <copy>.db"` and start the new build against the copy first.

### Network checks

- **IP changed:** update the Cloudflare A record **and** every local DNS override (AdGuard, MikroTik). A local override answers first, so leaving it behind keeps the dead address. Then run `ipconfig /flushdns` on each graphics PC and reload its browser sources. Nothing needs rebuilding.
- **Before the show,** run `nslookup valorant-gfx.noibo.beusesports.vn` on each graphics PC and compare the answer with the server's LAN interface address (`ip -4 addr show wlan0` or the Ethernet interface; ignore the 172.x Docker bridges). If the name does not resolve, the router may block DNS answers that point to private IPs. Add a DNS override on the router, or a hosts-file entry on that PC.
- **GStack:** inside the container, `localhost` is the container itself. Set the GStack URL in Settings to the GStack PC's LAN IP.

# Live Provider Transport Reference

Last updated: 2026-10-24

## Purpose

This document is the transport-level source of truth for live VALORANT provider integration.

It records:

- how the application connects to each provider;
- which upstream messages are considered authoritative observations;
- how full snapshots and incremental updates are handled;
- which provider fields are known, optional, enhanced, or still unresolved;
- which upstream values are normalized into the shared `LiveGameState`;
- which provider-specific values remain diagnostic/raw only;
- reconnect and resynchronization expectations;
- security rules for provider credentials and executable-looking payloads.

Implementation order, UI work, and Phase 6 acceptance remain in
[2026-10-03-phase-6-live-providers-external-hud.md](./2026-10-03-phase-6-live-providers-external-hud.md).

The normalized application model owns the graphics contract. Neither ValoSpectra nor GStack payload structures may leak into HUD components.

---

## 1. Shared transport rules

### 1.1 One upstream session

The Node server owns the active provider connection.

Opening additional:

- Graphics Control pages;
- embedded Previews;
- Large Preview;
- OBS/browser sources;

must not create additional ValoSpectra or GStack upstream sessions.

Browser clients receive the application's own read-only live-data stream, not a direct provider connection.

### 1.2 Provider data is observational

Providers may report:

- names;
- agents;
- weapons;
- health/shield;
- economy;
- K/D/A;
- abilities;
- ultimate state;
- scores;
- spike state;
- round outcomes;
- provider-side/team positions.

They do not silently rewrite canonical:

- Tournament entries;
- Match Team A / Team B;
- saved Game lineups;
- Map Veto;
- saved Agent Select;
- local team/player branding;
- operator broadcast presentation.

Provider identity is joined to local identity through the explicit Phase 6 mapping layer.

### 1.3 Missing is not zero

Provider blanks, absent auxiliary-client fields, malformed optional values, or unsupported fields normalize to `null`.

An observed numeric zero remains `0`.

Missing enhanced fields do not by themselves indicate a dead provider.

### 1.4 Raw data retention

Keep only the current/latest raw provider state required by View Data and diagnostics.

Do not persist every live tick to SQLite.

Credentials, access keys, or private provider configuration must never be included in:

- live SSE;
- OBS output;
- browser console output;
- View Data;
- raw diagnostic JSON returned to clients.

---

## 2. ValoSpectra

### 2.1 Services

Current integration uses two server-side endpoints.

| Purpose                       | Default service | Protocol  |
| ----------------------------- | --------------- | --------- |
| Live match state              | port 5200       | Socket.IO |
| Organization/supporter lookup | port 5101       | HTTP      |

Recommended configuration:

```text
SPECTRA_SOCKET_URL=http://localhost:5200
SPECTRA_EXTRAS_URL=http://localhost:5101
SPECTRA_ACCESS_KEY=
```

The exact host may be remote/configured; the access key is server-only.

### 2.2 Live Socket.IO session

The client connects with a Socket.IO-compatible library.

On connect:

```js
socket.emit(
	'logon',
	JSON.stringify({
		groupCode
	})
);
```

The server responds with `logon_success`.

After successful logon, consume `match_data` events.

Do not substitute a raw WebSocket client for Socket.IO.

A successful logon must be followed by usable `match_data` within five seconds. An acknowledgment alone does not establish usable telemetry; malformed data does not extend that deadline.

### 2.3 match_data handling

Treat each valid `match_data` event as the latest Spectra observation.

The Spectra adapter converts only the fields consumed by the application into `LiveGameState`.

The adapter should retain enough raw input in memory for View Data, but the raw object is never forwarded directly to OBS/browser SSE.

Provider-side team order is not Match Team A/B identity.

- `room` + `view=<id>` + `scene=0` selects one feed from the room. It does not make outer CSS hiding a VDO.Ninja scene-membership change. [View selection](https://docs.vdo.ninja/advanced-settings/mixer-scene-parameters/view)
- `_H_` is part of the naming scheme. These files do not establish a paired `_L_` publisher.
- Ten feeds at the requested `vb=5000` would total about 50 Mbps of video **if each achieved that target**, before transport/audio overhead. This is arithmetic, not observed traffic or a hard aggregate cap.
- The source is evidence of an implementation pattern, not proof that ten full-quality feeds perform well on this production machine.

**What to copy**

- Stable URL values and deliberate camera identity handling.
- Only initialize configured cameras; do not create empty iframe instances.
- Presentation options such as `cleanoutput`, `transparent`, `waitmessage`, and `disablehotkeys` where appropriate.
- Persistent camera ownership for this app's keep-warm requirement, including its ancestors.

**What not to copy blindly**

- Compare 1000–2500 kbps with higher targets at the actual displayed size; do not declare a universal sufficient bitrate from CSS dimensions alone.
- `codec=h265,av1,h264,vp8` is an ordered preference. Check the negotiated codec and decode performance in the installed Chrome/vMix versions. H264 can be a starting comparison, not a hardware-acceleration guarantee.

**Candidate fixed-view P2P URLs (untested)**

Both links intentionally use the same stream ID. The preview scale assumes a 720p source. Substitute URL-encoded room/stream values and add the deployment's room credentials and remote-control settings as needed.

```
HUD:     https://vdo.ninja/?room=<room>&view=<id>&scene=0&cleanoutput&transparent&disablehotkeys&waitmessage=Loading&codec=h264&vb=2000
Preview: https://vdo.ninja/?room=<room>&view=<id>&scene=0&cleanoutput&disablehotkeys&codec=h264&vb=200&scale=25
```

These illustrate per-view quality requests, not the consolidated director/scene implementation. Do not apply their quality assumptions to Meshcast, infer a 10 FPS limit, or put `maxvideobitrate=200` on the sender: that sender cap would also restrict the HUD viewer. Verify both connections' actual stats simultaneously.

| Preview / director     | Operator PC        | Ten low-quality P2P subscriptions with operator controls; evaluate consolidation into one director or mixer.                                              |
| Scoreboard HUD         | Production machine | Retain all ten camera connections and display the selected pair beside the scoreboard. Compare per-camera iframes with a preloaded controllable scene.    |

| Senders                | Player PCs         | Test 720p30 capture against all display surfaces; permit independent quality requests. Budget two or three internal receiving peers per player under P2P. |

Keep-warm describes the connection lifecycle. It does not require every hidden feed to run continuously at the active feed's quality. ## 5. Diagnostics checklist (for the next test)

Capture these, because the root cause is still unconfirmed:

1. **Establish the runtime and baseline.** Record browser/vMix versions, launch command, capture settings, and every open camera consumer. Use the built runtime from §3.6. Confirm graphics load with cameras disabled before adding media.
2. **Record startup evidence.** Capture console/network failures, a DevTools Performance trace, and Chrome task-manager CPU/memory by process. Compare no cameras, static iframe content, and real VDO.Ninja content; a static frame omits both app and media work and does not isolate which was responsible.
3. **Increase load deliberately.** Test 0, 1, 2, 5, then 10 camera sources. With all ten publishing, validate the 20-subscription HUD-plus-preview case and the 30-subscription case with a separate pregame pool. Compare simultaneous/staggered startup and 1080p60/720p30 with other variables held fixed. An improvement narrows the investigation but does not uniquely prove a keyframe storm.
4. **Measure both media endpoints.** Record per-connection bitrate, resolution, FPS, loss, keyframe requests, codec, and encoder/decoder information where exposed. Use VDO.Ninja stats and `chrome://webrtc-internals`; `chrome://gpu` shows capability/status, not proof of each stream's active decoder. [Stats troubleshooting](https://docs.vdo.ninja/guides/stats-menu/troubleshooting)
5. **Exercise keep-warm and host differences.** Repeatedly change the selected pair, hide/show the HUD and intro, and update scores while recording iframe loads, reconnects, black frames, and time to first/full-quality video. Check that Solo View opens VDO.Ninja directly and adds only the expected external subscription without restarting the internal receivers. Compare Chrome and vMix under matched loads. A difference identifies an environment dependency, not CEF as the proven root cause.

Use local looping video or stills for layout work. Those fixtures do not substitute for the live, multi-PC test on the production machine.
