# Phase 5.1 Graphics Control Workflow and Test GFX v2 Plan

> **For agentic workers:** This is a corrective operator-workflow pass on top of the completed Phase 5 broadcast foundation. Preserve the existing shared broadcast snapshot/SSE library, competition identity rules, and domain ownership. Do not create graphics-only copies of lineup, veto, agent, statistics, MVP, match, or game data.

**Goal:** Turn Phase 5's functional-but-fragmented Graphics Controller into an operator-friendly multi-page workspace, make Agent Select a first-class preparation step, add safe Game duplication, add embedded/large previews to every graphics control page, and refresh the generic test graphics so they are useful for workflow/data-source validation without pretending to be the final broadcast package.

**Architecture:** Keep the database and existing domain services as the source of prepared competition data. Graphics Control is another operational surface over the same records, not a second editor model. Reuse the existing typed broadcast snapshot and SSE client. Route each graphic to its own control page, share one Global Setup component/data loader, and embed the same management editors used elsewhere. Preview is an inspection surface, not a Preview/Program bus.

**Builds on:** [Phase 5 Broadcast Controls and Test Graphics Implementation Plan](./2026-10-01-phase-5-broadcast-controls-test-graphics.md).

**Status:** Planned after Phase 5 implementation review. This pass should land before Phase 6 provider integration so live-provider work is tested against the corrected operator workflow.

## Approved Phase 5.1 decisions

### Graphics Control information architecture

- /admin/graphics becomes the Graphics Control overview/index rather than one giant tabbed controller.
- Each graphic gets its own stable control route:
  - /admin/graphics/player-lineup
  - /admin/graphics/player-stats
  - /admin/graphics/map-veto
  - /admin/graphics/agent-select
  - /admin/graphics/in-game
  - /admin/graphics/post-game
  - /admin/graphics/mvp
- All of those routes belong to one **Graphics Control** navigation category.
- Do not require the operator to jump to Tournament/Match/Game management pages for ordinary graphics preparation.
- The normal management pages remain available and continue to edit the exact same persisted records.

### Shared Global Setup

Every Graphics Control page, including the overview, shows the same compact Global Setup surface:

- Tournament -> Match -> Game draft selection;
- explicit **Take game live** action;
- current live selection summary;
- connection/snapshot status;
- presentation Left/Right state and **Swap Left/Right**;
- current Attacker/Defender resolution and manual Phase 5 test override;
- readiness summary relevant to the selected game.

Changing a partial selector draft must not change the live game. Reuse the existing control revision/stale-write rules.

### Game management workflow

The Game workspace order is:

1. **Info**
2. **Lineup**
3. **Map Veto**
4. **Agent Select**
5. **Post-Game Report**

Rationale:

- Game identity/basic preparation comes first.
- The lineup must be known before composition.
- Map Veto/side choice occurs before teams finalize composition.
- Agent Select then records the player -> agent mapping.
- Post-Game Report consumes the saved lineup and saved player -> agent mapping.

### Agent ownership

- Agent Select is a first-class preparation editor.
- The Post-Game Report must **not** edit the agent assignment.
- In Post-Game Report, each saved agent is displayed as the locked agent for that player.
- Agent changes happen through Agent Select, not through the statistics table.
- Do not duplicate agent data into a second table: the canonical mapping remains the saved game's lineup/player assignment.
- Future provider/import behavior must merge into this same ownership model rather than creating a parallel agent field.

### Game duplication

Add a per-Game duplication workflow for quickly preparing the next game in the same match.

Default/safe semantics:

- new Game No.: required and must be an unused number valid for the match;
- new Game label/name: required, default from the target number;
- lineup: **copy by default**;
- agent assignments: **optional**, default OFF;
- map: **do not copy**; use the target Game No. and Map Veto projection;
- starting sides: **do not copy**; use the target Game No. and Map Veto projection;
- draft/final scores: **never copy**;
- result/winner: **never copy**;
- post-game statistics: **never copy**;
- MVP: **never copy**;
- statistics import/provenance metadata: **never copy**.

Duplication must be transactional and must not alter the source game.

### Preview surface

Every individual GFX Control page has an embedded Preview.

Desktop target:

    +--------------------------------------------------------------+
    | Global Setup                                                 |
    +--------------------------------------+-----------------------+
    | Graphic-specific controls/editors    | Preview               |
    | ~2/3                                 | ~1/3                   |
    |                                      | 16:9 scaled canvas     |
    |                                      | [Large Preview / TV]   |
    +--------------------------------------+-----------------------+

On narrower layouts the Preview may stack below the controls.

The Preview:

- renders the same actual graphic/template path used by the browser output;
- preserves the 1920x1080 composition and scales it to fit;
- updates when the saved/control snapshot changes;
- has a clearly labelled **Large Preview** action using a TV/monitor-style icon;
- Large Preview opens the graphic over the admin workspace in a lightbox/modal-style surface;
- Large Preview preserves aspect ratio and offers an obvious close action;
- neither embedded nor Large Preview changes what is visible on air.

Phase 5.1 does **not** introduce a separate Preview/Program state machine. There is no Take Preview, Preview bus, Program bus, or input switcher in this phase. The preview is an inspection surface over the current saved/control state. A future broadcast-output architecture may replace the preview source without requiring the control-page UX to be redesigned.

### Test GFX v2 scope

The redesigned generic graphics remain **test graphics**, not the final FPT Shop x Acer broadcast package.

Their purpose is to:

- make the operator workflow easy to validate visually;
- exercise all shared broadcast data paths;
- expose missing/awkward data states before Phase 6-8;
- test 1920x1080 browser-source composition;
- test missing assets, long names, incomplete preparation and side/presentation changes;
- provide realistic space planning for any required data-source attribution/watermark.

The ValoSpectra/Spectra frontend may be used as **inspiration/reference for quality, information hierarchy, motion and practical overlay composition**, but:

- do not copy its layouts;
- do not copy its artwork/assets;
- do not make the test package visually dependent on Spectra;
- do not treat the test package as the final event visual identity.

Where useful, Test GFX v2 should reserve a small attribution-safe area that can accommodate a Spectra watermark if Spectra is later the active datasource. Actual conditional datasource attribution belongs with provider integration once the source is known.

## Global constraints

- Preserve the existing Team A/B vs Left/Right vs Attacker/Defender separation.
- Team A remains competition/veto order. Graphics presentation swapping never changes Team A/B.
- Attacker remains blue and Defender remains red, independent of screen position.
- Preserve stable /gfx/live/[graphic] browser-source URLs.
- Preserve the shared broadcast snapshot and shared SSE client/library.
- Do not create a second persisted copy of management data for Graphics Control.
- Ordinary management browsing must not switch the live selection.
- Graphics Control pages may edit the canonical domain data through shared components/services.
- Unknown/incomplete data must remain representable and must not be invented.
- Final tournament artwork remains Phase 8.
- Live provider integration remains Phase 6.
- Post-game import remains Phase 7.
- Authentication remains outside this corrective pass unless another requirement explicitly pulls it in.
- Do not build a vMix/OBS-style full switcher only because a Preview surface exists.

## Task 0 — Restructure Graphics Control into a multi-page workspace

Replace the current all-in-one /admin/graphics tab workspace.

### Route structure

Keep /admin/graphics as an overview/index. Add one route per graphic under /admin/graphics/[graphic] or equivalent stable routes using the existing seven graphic IDs.

The overview should show:

- Global Setup;
- current live game;
- connection/readiness summary;
- cards/list items for all seven graphics;
- visible/hidden state where useful;
- a direct **Control** action for each graphic;
- optionally a direct clean-output link, but this must not be the primary editing workflow.

Each graphic page should show:

1. Global Setup;
2. page title/status;
3. graphic-specific editor/control surface;
4. embedded Preview;
5. Show/Hide or other graphic-specific broadcast controls.

### Navigation

Update the admin navigation so every /admin/graphics/* route highlights the single Graphics Control category.

Within Graphics Control, add a compact local navigation/menu for the seven controls. Do not reintroduce the old giant tab surface.

### Required behavior

- Browser history/back works naturally between graphic control pages.
- Direct links to any control page work after reload.
- Unsaved-edit protection still works when navigating away.
- Switching control pages never switches the live game.

## Task 3 — Split Agent Select from Post-Game Report

The current PostGameEditor combines agent assignment and post-game metrics. Separate those responsibilities.

### Dedicated Agent Select editor

Create a reusable Agent Select management component.

It should:

- show the selected game's saved lineup;
- preserve each player's team and lineup slot;
- offer one Agent selection per saved player;
- allow Unknown/unselected during preparation;
- support active agents and retain historical saved agents when needed;
- save all player -> agent assignments in one explicit action;
- use the game revision/stale-write rules;
- never edit K/D/A or post-game metrics.

Add a dedicated domain service/action such as saveGameAgents rather than routing agent changes through saveGameStatistics.

### Post-Game Report editor

Refactor PostGameEditor so:

- Player is read-only identity.
- Agent is read-only/locked identity taken from Agent Select.
- Statistics remain editable:
  - Kills
  - Deaths
  - Assists
  - Performance Score
  - Trades
  - First Bloods
  - Plants
  - Defuses
- Unknown remains NULL and measured zero remains 0.
- Existing provenance/manual-edit behavior remains intact.

If an agent is missing, Post-Game Report must show Unknown/Missing rather than offer an agent selector.

### Game workspace tab order

Change the Game workspace to exactly:

**Info -> Lineup -> Map Veto -> Agent Select -> Post-Game Report**

Map Veto remains match-wide even though it is accessible from the Game workspace.

### Regression requirement

Existing saved agent assignments must remain compatible; this is a UI/service ownership refactor, not a schema duplication or destructive migration.

## Task 4 — Add safe Game duplication

Add a duplicate action in the Match -> Games workflow, and optionally expose the same action from a Game page where convenient.

### Operator flow

For an existing source game:

1. choose **Duplicate**;
2. select an unused target Game No.;
3. enter/confirm the new Game label;
4. choose whether to copy Agent Select;
5. confirm duplication;
6. create the new game and open its Game workspace.

Lineup copy is on by default and does not need an extra opt-in unless UX testing proves otherwise.

### Domain service

Create one transactional service such as duplicateGame.

It must:

- revision-check the match;
- verify source game belongs to the match;
- validate the target game number against BO format and uniqueness;
- create the target through the same veto projection rules used by normal game creation;
- copy the source lineup to the target;
- copy agentId only when the operator requested it;
- leave scores/result/winner/MVP/statistics/provenance empty;
- leave source rows untouched;
- recompute/return series state exactly as normal creation does.

Do not implement duplication by cloning the complete games row and deleting unwanted fields afterward.

### Veto precedence

The target game's map and starting sides are determined from the target Game No.'s current veto projection. Source map/sides never override the target veto.

## Task 5 — Add embedded Preview and Large Preview

Build one reusable preview component used by all seven Graphics Control pages.

### Embedded Preview

Target desktop layout is approximately a **2/3 controls + 1/3 preview** grid.

The preview frame should:

- be visually identifiable as Preview;
- show a 16:9 representation;
- scale the real graphic without changing its internal 1920x1080 coordinate system;
- avoid introducing scrollbars inside the preview;
- handle transparent content against an intentional checker/dark preview background;
- expose loading/disconnected/no-selection states clearly;
- update after saved domain/control changes via the existing broadcast refresh path.

Prefer reusing the actual graphic/template rendering boundary instead of rebuilding "mini preview" markup.

### Large Preview

Add a TV/monitor icon button beside the preview header.

Large Preview should:

- open over the current admin view;
- use most of the available viewport;
- preserve 16:9;
- use the same graphic source/state as the embedded preview;
- close via visible button and Escape;
- trap/restore focus appropriately;
- not navigate away from the editor;
- not mutate broadcast state.

### Explicit boundary

This is **not** a broadcast Preview/Program implementation.

Do not add:

- Preview selection persisted on the server;
- Program selection separate from the existing live selection;
- TAKE/CUT/AUTO;
- Preview-to-Program;
- input switching;
- a compositor solely for this feature.

If browser-rendering limitations later require a different production architecture, preserve the control-page Preview UX and replace its rendering source behind the component boundary.

## Task 6 — Redesign the generic package as Test GFX v2

Do this after the operator-workflow refactor so the new previews exercise the real final Phase 5.1 control surfaces.

Keep:

- 1920x1080 transparent output;
- all seven graphics;
- current template-resolution/fallback contract;
- shared typed broadcast client/selectors;
- missing-data-safe behavior.

Improve the generic visuals enough that they are useful for realistic testing.

### Visual principles

Use the existing project screenshots/current graphics and public Spectra frontend as references for problems/solutions, not as artwork to reproduce.

Aim for:

- stronger visual hierarchy;
- consistent spacing and typography;
- clear team identity;
- symmetric layouts where appropriate;
- clear Attacker-blue / Defender-red treatment where gameplay side matters;
- deliberate map/agent/player imagery;
- safe treatment of long names and absent imagery;
- simple, restrained transitions useful for browser-source testing;
- consistent attribution-safe area.

Avoid:

- copying Spectra's exact composition;
- importing Spectra artwork;
- making the graphics look like final sponsor-approved FPT Shop x Acer deliverables;
- spending Phase 5.1 effort on a full final-brand motion package.

### Spectra attribution test

Provide a documented/testable safe placement for a Spectra attribution/watermark when Spectra is the datasource.

Phase 5.1 may use a development-only placeholder to prove the safe area. Do not hard-code a permanent Spectra watermark into every graphic when the actual source is unknown.

### Graphic-specific intent

**Player Lineup**
- clearly show 5v5 identities;
- stress-test names/portraits/logos.

**Player Stats**
- make single and head-to-head modes obviously distinct;
- handle unsupported/missing broader-scope metrics clearly.

**Map Veto**
- prioritize action sequence, actor, map and game assignment readability.

**Agent Select**
- show the locked player identity and selected agent as two distinct concepts;
- make map and side context visible without copying Spectra's layout.

**In-Game**
- remain native-HUD-safe;
- do not fabricate Phase 6 live telemetry.

**Post-Game**
- prioritize score, player-agent identity and Phase 4 metrics;
- keep unavailable values explicit.

**MVP**
- feature the operator-selected MVP and relevant saved context without inventing a rating.

## Task 7 — Browser and regression verification

Add focused automated tests around the corrected operator workflow.

### Journey A — Graphics Control routing

1. Load /admin/graphics.
2. Select/take a game live.
3. Navigate through all seven control pages.
4. Verify the same live selection/global state remains.
5. Verify browser back/forward works.
6. Verify a partial selector draft does not change live output.

### Journey B — Inline canonical editing

1. Open Player Lineup control.
2. Edit/save lineup without navigating to /admin/games/....
3. Verify normal Game -> Lineup reflects the same saved data.
4. Open Map Veto control.
5. Edit/save veto.
6. Verify Match/Game management reflects the same saved data.

### Journey C — Agent Select -> Post-Game

1. Save a lineup.
2. Save agents in Agent Select.
3. Open Post-Game Report.
4. Verify player and agent identity are shown and agent is not editable.
5. Save statistics.
6. Verify Agent Select assignment remains unchanged.
7. Verify the output snapshot shows the saved player-agent mapping and metrics.

### Journey D — Game duplication

1. Prepare Game 1 with lineup, agents, map/sides, scores, stats and MVP.
2. Duplicate it to a valid unused game number with agent copy OFF.
3. Verify lineup copied.
4. Verify target map/sides come from its veto projection.
5. Verify agents, result, score, statistics, MVP and provenance are empty.
6. Repeat with agent copy ON and verify only agents additionally copy.
7. Verify source Game 1 is unchanged.

### Journey E — Preview

For every graphics control page:

1. embedded preview renders the correct graphic;
2. saved edits refresh it;
3. Show/Hide/current controls behave as expected;
4. Large Preview opens without navigation;
5. Escape/close returns focus;
6. Large Preview and embedded Preview show the same state;
7. neither preview changes broadcast control state.

### Journey F — identity axes regression

Repeat the established Phase 5 checks:

- Team A/B remains stable competition identity;
- Swap Left/Right changes presentation only;
- Attacker/Defender changes color semantics only;
- Map Veto actors do not follow presentation swap.

### Journey G — Test GFX v2 edge states

Capture deterministic screenshots for:

- complete preparation;
- incomplete lineup;
- missing agent;
- missing portrait/logo;
- long team/player names;
- no live selection;
- both presentation orders;
- both attacker/defender assignments;
- Player Stats single/head-to-head;
- attribution placeholder safe area.

Do not call visual screenshots "final design acceptance."
