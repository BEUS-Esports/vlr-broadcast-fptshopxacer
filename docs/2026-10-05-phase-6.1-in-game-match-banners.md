# Phase 6.1 In-Game Match Banners Plan

> **For agentic workers:** This is an operator-owned in-game presentation layer on top of the completed Phase 5/5.1 broadcast controls and Phase 6 provider HUD foundation. Tactical Timeout, Technical Pause, and ceremony controls belong to our broadcast state, not to Spectra/GStack telemetry. The Native HUD and Live Data HUD must consume the same controls and the same shared banner renderer. Do not add provider-specific pause/ceremony logic to `LiveGameState` in this phase.

**Goal:** Add the missing center-screen match banners used during live VALORANT play: Tactical Timeout, Technical Pause, and manually triggered round ceremonies (Round Win, Thrifty, Clutch, Team Ace, Flawless). The controls must work identically with the Native HUD and the provider-backed Live Data HUD, remain safe under multiple operators, and preserve the existing Preview/Program behavior.

**Architecture:** Extend the existing persisted broadcast live-control state rather than creating another graphics bus. Pauses are persistent operational state with an explicit transition state machine. Ceremonies are short-lived timestamped trigger events. A single shared center-banner component is rendered above either in-game HUD path from the common `GraphicRenderer` boundary. Provider telemetry continues to describe gameplay observations only.

**Builds on:**

- [Phase 5.1 Graphics Control Workflow and Test GFX v2](./2026-10-02-phase-5.1-graphics-control-workflow-test-gfx-v2.md)
- [Phase 6 Live Providers and External HUD](./2026-10-03-phase-6-live-providers-external-hud.md)

**Reference direction:** `nobiiVAL/Spectra-Frontend-VAL26` places end-round and timeout/technical-pause treatments in the upper-center gameplay area, roughly 733-788px wide and about 178-185px tall. Use that positioning/information hierarchy as a reference only. Do not copy its SVGs, fonts, artwork, source structure, or animations.

**Status:** Implemented 2026-10-05 on `phase-6.1-match-banners`, based on Phase 6 head `5b49b3ef`. The operator reports migration 0009, its related actions, and HUD composition working. Real-provider Live Data testing remains pending because provider access is currently unavailable. See [verification and remaining acceptance](./2026-10-05-phase-6.1-verification.md).

**Implementation clarifications:** Keep the v2 compatibility path confined to persisted publication loading; validate the entire old shape before inserting safe defaults. The existing Program selector already overlays the complete latest `liveControls`, so extend that contract and retain its publication behavior. Ceremony enter/exit motion must fit the original absolute six-second window and must never leave two banners in the shared slot during a transition. Automated implementation verification and real VALORANT/OBS composition acceptance are separate outcomes; record the latter as pending until tested on the actual capture.

## Approved Phase 6.1 decisions

### One app-owned control surface for both HUDs

Tactical Timeout, Technical Pause, and round ceremonies are controlled by this application.

They are **not** sourced from or synchronized back to ValoSpectra/GStack in Phase 6.1.

This applies equally to:

- the Native In-Game HUD;
- the Live Data HUD with Spectra;
- the Live Data HUD with GStack;
- Live Data Preview before provider mapping;
- operation with no provider connected.

The provider layer must not need to know that a pause or ceremony was triggered.

### Pause state is operational state, not a graphic toggle

Only one pause state may exist at a time.

Supported states:

```ts
export type BroadcastPauseState =
	| { type: 'none' }
	| {
			type: 'tactical';
			entryId: string;
			pendingTechnical: boolean;
	  }
	| { type: 'technical' };
```

Rules:

1. From `none`, either team may start a Tactical Timeout, or the operator may start a Technical Pause.
2. A second Tactical Timeout cannot replace an active Tactical Timeout.
3. A Technical Pause cannot visually replace an active Tactical Timeout.
4. If a technical issue is recognized during a Tactical Timeout, set `pendingTechnical: true`.
5. Finishing that Tactical Timeout transitions **atomically** to Technical Pause when `pendingTechnical` is true. There must be no intermediate idle/blank state.
6. A Tactical Timeout cannot be started while Technical Pause is active.
7. Technical Pause remains active until the operator explicitly resumes.
8. Permit the operator to cancel a pending Technical Pause before finishing the Tactical Timeout, as an error-correction path.
9. Changing/clearing the selected live game clears all pause state.

No tactical countdown is required in Phase 6.1.

No timeout-remaining counter is required in Phase 6.1.

The event policy may still grant two regulation timeouts per team and one fresh overtime timeout per team, but this phase deliberately does not track/enforce those counts.

### Ceremonies are transient trigger events

Supported ceremony types:

```ts
export const ceremonyTypes = ['round-win', 'thrifty', 'clutch', 'team-ace', 'flawless'] as const;
```

Each trigger identifies one local tournament entry and one ceremony type.

Suggested contract:

```ts
export type BroadcastCeremonyType = (typeof ceremonyTypes)[number];

export type BroadcastCeremonyEvent = {
	sequence: number;
	type: BroadcastCeremonyType;
	entryId: string;
	triggeredAt: number;
} | null;
```

Semantics:

- `sequence` identifies a new trigger even when two successive rounds use the same team and ceremony type.
- Use the revision produced by the trigger write as the sequence; do not add another independent sequence generator unless implementation constraints require it.
- Start with one shared `CEREMONY_VISIBLE_MS = 6000` constant. The exact visual timing may be tuned without changing persistence/schema semantics.
- A stale ceremony remains harmless in persistence: render it only while the sampled server time is before `triggeredAt + CEREMONY_VISIBLE_MS`.
- Do not replay an expired ceremony after reload/reconnect.
- Do not silently stack ceremonies.
- Reject a second ceremony while the prior ceremony is still active. Provide **Dismiss Ceremony** as an operator correction path if the wrong ceremony/team was triggered.
- Block a new ceremony trigger while a pause is already active.
- If a pause begins while an already-triggered ceremony is still playing, allow the ceremony to finish and then reveal the pause banner. The pause state itself becomes active immediately; only its visual presentation waits for the ceremony.
- Changing/clearing the selected live game clears the stored ceremony event.

### Server time and broadcast LAN synchronization

The server owns `triggeredAt`, expiry validation and the six-second deadline. The existing broadcast SSE emits a `clock` event containing server epoch milliseconds immediately before each snapshot (including cached reconnects), and every 15 seconds as its heartbeat. Each client advances that sample with `performance.now()`; banner rendering and operator expiry gating use the same per-connection clock. Wait for a valid clock sample before showing a ceremony or enabling its trigger. Clock samples do not change snapshot/publication contracts or stream cursors.

This removes reliance on matching browser wall clocks. Receive-time sampling still includes one-way network latency and browser scheduling delay; it is suitable for this LAN ceremony window, not frame-accurate synchronization.

Keep the app server, OBS/graphics and replay machines synchronized through NTP or the managed domain time service, preferably using the same managed source. Before a broadcast on Windows, check `w32tm /query /status` and `w32tm /query /source` on each machine; confirm a recent successful synchronization and a real time source. If synchronization is stale, correct the configured service/source and run `w32tm /resync` from an elevated terminal. These are deployment checks; the app does not change system clocks or configure NTP. Clock synchronization remains an operational recommendation, not a Phase 6.1 blocker.

### Shared center-banner slot

All Phase 6.1 banners occupy one shared upper-center match-banner region.

Initial 1920x1080 target:

- horizontally centered;
- initial top anchor around **200px**;
- target width roughly **740-790px**;
- target height no more than roughly **185px**;
- below the top scoreboard/timer treatment;
- above the Live Data HUD player rails that begin around y=385;
- no overlap with the native upper-right killfeed.

The exact safe-area position is accepted through 1920x1080 screenshots and real Valorant/OBS composition testing, not by copying a reference pixel-for-pixel.

### Team identity and side colors

Banner team ownership always uses the **local tournament entry ID**.

Do not store Team A/B, Left/Right, or provider side as the banner identity.

Presentation rules:

- display local team name/tag/logo when available;
- determine current Attacker/Defender from the existing broadcast side selectors;
- Attacker accent remains blue;
- Defender accent remains red;
- if current side is unknown, use the neutral treatment;
- Left/Right swap must not change which team owns a timeout or ceremony.

Provider mapping is irrelevant to banner ownership.

### Preview and Program

Pause/ceremony state is a live broadcast control like current side/swap, not held prepared content.

Therefore:

- normal Native Preview reflects current banner controls;
- Live Data Preview reflects the same current banner controls, even with no provider data;
- Large Preview does the same;
- a shown In-Game Program output receives pause/ceremony changes immediately without Hide -> Show;
- triggering a banner must not recapture the In-Game publication;
- all connected outputs receive the same control state/event.

## Task 2 - Add server-owned pause transition commands

Do not expose a generic "set pause object" write.

Extend the existing revision-checked Graphics Control action/service with explicit intents, for example:

```ts
type InGameControlAction =
	| { type: 'start-tactical'; entryId: string }
	| { type: 'request-technical' }
	| { type: 'cancel-pending-technical' }
	| { type: 'finish-tactical' }
	| { type: 'resume-technical' };
```

Exact form encoding may differ, but the server must own transitions.

### Required transitions

```text
NONE
  + start tactical A/B -> TACTICAL(team)
  + request technical  -> TECHNICAL

TACTICAL(team)
  + request technical          -> TACTICAL(team, pendingTechnical=true)
  + cancel pending technical   -> TACTICAL(team, pendingTechnical=false)
  + finish, pending=false      -> NONE
  + finish, pending=true       -> TECHNICAL

TECHNICAL
  + resume -> NONE
```

Everything else is rejected as invalid/blocked.

### Validation

- require a selected game;
- Tactical Timeout entry must be one of the selected match participants;
- do not accept Team A/B or Left/Right strings in place of entry ID;
- reject start Tactical while Technical Pause is active;
- reject another Tactical while Tactical is active;
- reject `finish-tactical` outside Tactical state;
- reject `resume-technical` outside Technical state;
- reject/correct stale writers through existing `expectedRevision`;
- all state mutation and revision change occur atomically.

Do not make provider health/mode/mapping part of pause validation.

### Focused proof

Use service tests for every valid transition and every forbidden edge, including two stale controllers attempting conflicting transitions.

## Task 3 - Add server-owned ceremony trigger commands

Add explicit ceremony actions, e.g.:

```ts
type CeremonyAction =
	| {
			type: 'trigger-ceremony';
			ceremony: BroadcastCeremonyType;
			entryId: string;
	  }
	| { type: 'dismiss-ceremony' };
```

### Trigger rules

- require a selected game;
- entry must be one of the selected match participants;
- ceremony type must be one of the five allowlisted types;
- reject triggering while pause state is already Tactical or Technical;
- determine whether the prior ceremony is still active using server time and `CEREMONY_VISIBLE_MS`;
- reject another trigger while an existing ceremony is still active;
- successful trigger stores `triggeredAt = Date.now()`;
- successful trigger uses the new control revision as its unique sequence;
- dismiss clears the event but does not need to rewind any sequence;
- dismissing null/expired state may be treated as an idempotent no-op or clear, but must never resurrect an event.

A pause command may begin while a ceremony is active; this is permitted because visual arbitration happens in the shared banner renderer.

### Focused proof

- five valid ceremony types;
- invalid string rejected;
- wrong-team entry rejected;
- repeated same ceremony receives a new sequence after the old event expires/dismisses;
- active ceremony rejects a second trigger;
- pause-active trigger is rejected;
- stale/expired persisted ceremony does not block a later valid trigger.

## Done when

Phase 6.1 is implementation-complete when the software requirements below are met. Live composition acceptance is a separate operational check:

- Native HUD and Live Data HUD use one shared app-owned center-banner layer.
- Tactical Timeout is tied to a local team entry and never to presentation/provider side identity.
- Technical Pause cannot replace an active Tactical Timeout; it can be queued and begins atomically when Tactical finishes.
- Tactical Timeout cannot begin during Technical Pause.
- Round Win, Thrifty, Clutch, Team Ace, and Flawless can be manually triggered for either local team.
- Ceremony triggers are unique, transient, do not replay after expiry, and do not stack.
- An already-running ceremony may finish before a newly active pause is presented.
- Pause and ceremony control changes reach shown Program output immediately without Hide -> Show or publication recapture.
- Native Preview, Live Data Preview, and both Large Previews show the same control state.
- No provider session/control call is needed for any Phase 6.1 feature.
- Stale/direct requests cannot violate the server-owned transition rules.
- Existing v2 held publications survive the snapshot-contract upgrade safely.
- Automated tests cover transition, expiry, multi-controller, preview/program, and missing-provider cases.
- For live composition acceptance, Native HUD real Valorant/OBS composition is accepted; external-HUD composition remains tied to the separately pending real provider session when necessary.
